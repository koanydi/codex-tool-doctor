# 使用指南

Codex Tool Doctor用于诊断和处理第三方API工具协议不兼容导致的Codex工具不可用问题。它通过对照检测找到可能适用的模型目录补丁，再由所选Codex程序验证实际终端调用；只有验证通过才安装。认证、限流、服务停机、证书或系统权限错误需要按各自原因处理。

技术原理见[设计说明](设计说明.md)，测试方法与成功判据见[验证指南](验证指南.md)，版本变化见[CHANGELOG](../CHANGELOG.md)。

## 1. 平台启动与运行环境

先完整解压发布包，再进入工具目录运行命令。Windows示例使用PowerShell7；`doctor.cmd`前的`.\`表示当前目录。

| 平台 | 图形界面 | 命令行菜单 |
| --- | --- | --- |
| Windows | 双击`doctor-gui.cmd` | `.\doctor.cmd menu` |
| macOS | 双击`doctor.command`，或运行`sh doctor-gui.sh` | `sh doctor.sh menu` |
| Linux | `sh doctor-gui.sh` | `sh doctor.sh menu` |

macOS解压后若丢失可执行位，可运行`chmod +x doctor.command`，也可直接使用`sh doctor-gui.sh`。无图形桌面时使用CLI。

GUI在本机浏览器打开，仅监听`127.0.0.1`。需要自行打开浏览器时运行：

```powershell
.\doctor.cmd gui --no-open
```

```sh
sh doctor.sh gui --no-open
```

使用启动时输出的完整地址，包括`#`后的会话令牌。关闭浏览器标签页不会停止服务，应在启动终端按Ctrl+C或结束该GUI进程。GUI端口仅用于操作界面，不承担Codex请求转发。

### 自动准备环境

平台启动器优先复用可运行的Node.js22或更新版本。缺少Node、版本过旧或需要补齐npm时，先检查便携缓存，再按随包清单从Node.js官方HTTPS地址下载，优先选择清单中的24系列，兼容失败时尝试22系列。下载须通过SHA-256校验、暂存解压和Node/npm可执行检查后才进入稳定目录。

依赖缺失、版本不符或实际导入失败时，启动器自动运行`npm ci --ignore-scripts`并重新检查。安装最多尝试3次，后两次明确使用官方npm源；准备完成后继续原来的GUI或CLI命令。普通应用错误不会触发循环重装。

| 平台 | 默认便携运行时目录 | 缺少Node时需要的系统工具 |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\CodexToolDoctor\runtimes` | Windows Script Host、tar、certutil；优先curl，缺少curl时尝试系统HTTPS组件 |
| macOS/Linux | `$XDG_DATA_HOME/codex-tool-doctor/runtimes`；未设置时为`~/.local/share/codex-tool-doctor/runtimes` | POSIX sh、curl、tar及sha256sum、shasum或openssl之一 |

`TOOL_DOCTOR_RUNTIME_DIR`可指定便携缓存目录。启动器支持Windows/macOS/Linux的x64与ARM64选择；Linux musl的自动安装分支限x64，实际可用性还取决于清单和系统能否运行相应Node归档。

自动准备在当前用户权限下完成，不全局修改PATH。首次缺少环境时需要联网，项目目录和缓存目录需要可写；已有运行时及依赖正常时不因启动而下载安装。断网、企业策略禁用脚本宿主、缺少系统工具或操作系统不支持相应Node版本时，按错误提示恢复条件后重新启动。

自动准备范围是本工具的Node/npm和项目依赖。目标Codex程序须另行安装；Windows终端验证还需要可用的PowerShell7。仅由启动器准备的便携Node不一定能在终端用裸`node`或`npm`调用，日常操作统一使用平台入口。

### 完整发布包

完整可运行发布包包含平台入口`doctor.cmd`、`doctor.sh`、`doctor-gui.cmd`、`doctor-gui.sh`、`doctor.command`，以及`src/`、必要的环境准备脚本、`package.json`、`package-lock.json`、smol-toml依赖、中文文档和第三方声明。请保留包内相对目录结构；下载包另附`SHA256SUMS.txt`用于校验。

不要只复制一个启动脚本。便携Node按需准备，完整发布包不表示首次启动可以在缺少环境时离线安装。用户包不包含个人配置、密钥、备份、测试私钥或mock服务；开发测试请使用源码目录，按验证指南操作。

## 2. 配置HTTP、HTTPS与认证

默认配置目录由`CODEX_HOME`指定，未设置时为当前用户的`.codex`目录。工具读取其中的`config.toml`；`--home`可指定其他目录。保留自己的模型名，按路由服务要求配置地址：

```toml
model = "你的模型名"
model_provider = "router"

[model_providers.router]
name = "第三方Responses路由"
base_url = "http://127.0.0.1:3000/v1"
wire_api = "responses"
requires_openai_auth = false
# 路由需要密钥时，取消下一行注释并提前设置环境变量。
# env_key = "ROUTER_API_KEY"
```

目标服务必须提供Responses兼容接口。仅有Chat Completions接口的服务不能通过这个补丁直接使用；`wire_api`不为`responses`时会拒绝继续。

### 地址与路径

| `base_url`示例 | 诊断请求路径 |
| --- | --- |
| `http://127.0.0.1:3000` | `/responses` |
| `http://localhost:3000/v1/` | `/v1/responses` |
| `http://[::1]:3000/v1/responses` | `/v1/responses` |
| `http://192.168.1.10:3000/router/api/v1` | `/router/api/v1/responses` |
| `https://127.0.0.1:3443/router/v1` | `/router/v1/responses` |

工具保留端口和路径前缀，只拼接一次`/responses`，不会擅自添加`/v1`。路径由服务方确认；HTTP重定向不会自动跟随。

回环地址、私有及链路本地IP、`.localhost`、`.local`和单标签主机名默认允许HTTP。其他HTTP地址需要显式传入`--allow-insecure-http`；此参数仅允许本工具使用明文连接，不解决路由、认证或协议兼容问题。局域网HTTP同样没有TLS加密。

URL不得包含用户名、密码、片段或内嵌查询参数。查询参数、静态请求头和环境变量请求头分别放在provider内，例如：

```toml
# 以下行放在[model_providers.router]表内。
query_params = { "api-version" = "服务要求的版本" }
http_headers = { "X-Client-Name" = "codex-tool-doctor" }
env_http_headers = { "X-Router-Key" = "ROUTER_HEADER_KEY" }
```

环境变量请求头使用变量名，不能填写密钥值；需提前设置对应变量。请求头不能包含换行，也不能覆盖Host、Content-Length、Connection或Transfer-Encoding。

### 内置openai与自定义provider

选择内置`openai`时（包括省略`model_provider`），只更改服务地址可使用顶层`openai_base_url`，最终仍按Responses地址规则解析：

```toml
model = "你的模型名"
model_provider = "openai"
openai_base_url = "https://你的服务地址/v1"
```

本工具无法确认`[model_providers.openai]`中的覆盖与目标Codex实际采用的配置一致，因此采用保守策略：所选provider为`openai`且同名表非空时，在读取配置阶段拒绝诊断和验证。这不是对所有Codex版本支持情况的实测结论。工具不会在隔离验证中自动改名后为原配置生成成功记录。

需要`env_key`、`http_headers`、`env_http_headers`、`query_params`或其他provider字段时，请在实际使用的配置中同时把`model_provider`改为自定义名称（例如`router`），并把表名改为`[model_providers.router]`，保留所需字段。原来使用顶层`openai_base_url`的，还须把该地址移到自定义表的`base_url`。profile配置按与基础配置合并后的结果检查；请同步修改真正生效的配置层。

迁移后若仍要使用原账户API密钥，须在自定义表显式设置`requires_openai_auth=true`；使用独立路由密钥则配置`env_key`或对应请求头，无需账户认证时设为false。修改实际配置后重新诊断、验证，再安装候选。

### 凭据来源

诊断优先读取显式`env_key`，其次是`experimental_bearer_token`。第三方provider只有显式设置`requires_openai_auth=true`时才读取所选配置目录`auth.json`中的`OPENAI_API_KEY`，再尝试同名环境变量；省略该字段或设置为false时，不借用账户凭据。内置openai提供方保留默认的账户认证语义；需要改变认证方式时，按上一节迁移到自定义provider。自定义API密钥推荐用`env_key`或对应请求头提供。

自定义`http_headers`和`env_http_headers`在Bearer头之后合并，同名请求头以后者为准。工具不使用ChatGPT会话令牌；配置了外部`auth.command`时会停止诊断，需改为`env_key`等受支持的凭据方式。

### HTTPS与自建CA

HTTPS保持正常证书校验。使用自建CA时，先准备PEM格式CA证书，再在启动本工具之前设置`NODE_EXTRA_CA_CERTS`。以下`certs/router-ca.pem`是待替换的证书位置示例：

```powershell
$env:NODE_EXTRA_CA_CERTS = (Resolve-Path './certs/router-ca.pem').Path
.\doctor.cmd diagnose
```

```sh
export NODE_EXTRA_CA_CERTS="$(pwd)/certs/router-ca.pem"
sh doctor.sh diagnose
```

服务证书的SAN须匹配实际访问的IP或主机名；用`127.0.0.1`连接时，仅包含`localhost`的证书不够。设置后应重新启动已有GUI或维护进程，不要关闭TLS校验来绕过证书错误。

`NODE_EXTRA_CA_CERTS`用于本工具的Node诊断进程。真实Codex使用自己的网络实现，Node诊断成功不能证明Codex已信任同一CA；其证书信任仍需按目标客户端配置，并由真实候选验证确认。运行时下载所用curl或系统HTTPS组件也有各自的信任配置。

### 多配置与多安装

`--profile work`将基础`config.toml`与`work.config.toml`合并读取，补丁写入命名配置文件，状态放在独立profile目录。名称仅允许字母、数字、下划线和短横线。旧式`[profiles.*]`或`profile`配置会被拒绝，应先迁移配置层。

每个受管配置只对应一个所选Codex程序。桌面端和CLI可能携带不同后端，应选择实际出问题的程序，必要时使用独立`CODEX_HOME`或profile。以下占位符需要替换：

```powershell
.\doctor.cmd inspect --home "<配置目录>" --profile work --binary "<Codex原生可执行文件>"
```

后续诊断、计划、应用、维护和回滚须使用同一组`--home`与`--profile`；涉及目标程序时保持`--binary`一致。公网HTTP配置还须保持相应显式选项。

## 3. 诊断、验证与安装

GUI中先填写配置目录、profile和目标程序，再依次执行“开始诊断”“生成计划”“验证并安装”。“一键检测并修复”整合这些步骤；已有受管补丁时执行主动复检维护。

Windows命令行流程：

```powershell
.\doctor.cmd inspect
.\doctor.cmd diagnose
.\doctor.cmd plan
.\doctor.cmd apply
.\doctor.cmd status
```

macOS/Linux命令行流程：

```sh
sh doctor.sh inspect
sh doctor.sh diagnose
sh doctor.sh plan
sh doctor.sh apply
sh doctor.sh status
```

逐条查看结果再进入下一步。`diagnose`默认发送8次虚拟工具请求，但不执行返回的虚拟工具。两组平铺工具连续正常且包装格式出现特有失败时，才允许生成候选；诊断中的“候选可验证”不是修复成功。

`apply`先启动两轮隔离的真实Codex会话，仅请求Windows的PowerShell7执行`Get-Location`，或macOS/Linux执行`pwd`。两轮都须满足终端事件、退出码、工作目录和回合完成等判据；命令成功完成后、回合完成前，同一条模型确认消息还须包含工具输出中的实际目录与本轮随机确认标记。命令前的确认或仅重复标记不能通过。验证失败不会安装候选；报告中说明具体原因。

诊断和真实终端验证均会访问所选服务并消耗API额度。安装完成后重启对应Codex并新建会话，再检查实际使用场景。旧会话、所有插件、图像工具、文件编辑和桌面UI行为不在这项终端验证的保证范围内。

| 命令 | 作用 |
| --- | --- |
| `inspect`、`status` | 查看配置、补丁状态；`inspect`还检查目标程序和内置目录，不向模型服务发送诊断请求 |
| `diagnose`、`plan` | 保存诊断报告、生成并让目标程序解析候选目录，不安装候选 |
| `apply`、`repair` | 经验证后备份并安装，或复检现有受管补丁 |
| `verify` | 验证当前配置；`--catalog`可选择临时候选，不安装补丁 |
| `maintain`、`launch` | 维护受管补丁；`launch -- <Codex参数>`先维护，再启动目标程序 |
| `guard`、`guard-install`、`guard-uninstall` | 前台持续维护、安装或卸载当前用户维护服务 |
| `rollback`、`recover` | 撤销受管补丁、恢复中断的安装事务 |

`--repeats`为每种诊断格式的轮数，范围2～5，默认2；`--timeout`为单次API诊断请求超时，范围5～120秒，默认30秒，不改变真实终端验证的超时。真实终端验证每轮默认90秒。`--json`输出机器可读结果，更多参数使用`doctor.cmd --help`或`sh doctor.sh --help`查看。

## 4. 升级维护与停用

补丁保存在配置和外置模型目录中，没有预设到期时间。但外置目录包含完整模型元数据，必须随目标构建、模型和配置变化重新评估，不能承诺永久适用于任意未来版本或服务端协议。

```powershell
.\doctor.cmd maintain
.\doctor.cmd maintain --recheck
.\doctor.cmd guard-install
```

```sh
sh doctor.sh maintain
sh doctor.sh maintain --recheck
sh doctor.sh guard-install
```

`maintain`发现程序、内置模型目录、相关配置或模型变化时重新检测并验证；没有变化时不请求API。服务端协议可能在本机文件不变时发生变化，此时使用`--recheck`或`repair`主动复检。

受管区块被完整移除且没有其他目录覆盖时，可以重新验证后建立覆盖；目录丢失时可以重建。区块部分被修改、目录内容被修改或出现外部覆盖时，维护停止以保留编辑。更新失败保留已有补丁，但这不保证旧补丁仍适用于已升级程序。

如果目标构建原生使用完整Responses，或服务的四组诊断均通过，维护仍须先验证未修改的内置目录，两轮通过后才移除受管覆盖。条件成立本身不能写成“原生修复成功”。

| 平台 | 登录维护方式 |
| --- | --- |
| Windows | 当前用户的任务计划 |
| macOS | 当前用户LaunchAgent |
| Linux | systemd用户服务 |

成功安装补丁后才可运行`guard-install`，安装时会立即启动维护。服务记录项目脚本和Node的实际路径；移动或删除项目、运行时前，应先卸载服务，搬迁后重新安装。服务进程还必须能读取所需API密钥、请求头变量和CA设置，终端中的临时环境变量不一定进入登录服务。

`guard`默认每60秒检查，`--interval`可设15～3600秒，`--once`只检查一次。失败后退避，最长每小时重试；状态变化写入`last-guard.json`，后台不弹出通知，也不结束已有Codex会话。没有可用用户服务时可运行`sh doctor.sh guard`，或使用平台入口的`launch`命令进行启动前维护。

停止使用时，若启用了登录维护，先卸载它，再回滚；直接删除受管区块可能被维护重新建立：

```powershell
.\doctor.cmd guard-uninstall
.\doctor.cmd rollback
```

```sh
sh doctor.sh guard-uninstall
sh doctor.sh rollback
```

未安装维护服务时直接回滚即可。自动发现可跟踪原安装渠道；显式固定的`--binary`路径若在升级后失效，需要重新选择。

## 5. 备份、恢复与手动处理

状态默认位于`<CODEX_HOME>/tool-doctor/`，命名配置使用其下的`profiles/<名称>/`。这里的`<CODEX_HOME>`指实际选定的配置目录。

| 文件或目录 | 用途 |
| --- | --- |
| `last-report.json` | 诊断样本、请求状态、脱敏摘要、`blockers`和`warnings` |
| `last-plan.json`、`plans/<id>/` | 候选计划、模型目录和用于生成补丁的原配置 |
| `last-verification.json` | 两轮终端结果及与候选匹配的校验信息 |
| `active.json` | 当前受管补丁、目标构建、备份位置和验证记录 |
| `backups/<id>/config.toml` | 去除受管覆盖后的恢复基线 |
| `backups/<id>/before-transaction.toml` | 本次安装或更新之前的完整配置 |
| `transaction.json`、`operation.lock` | 未完成的安装事务、互斥操作锁 |
| `last-maintenance.json`、`last-guard.json` | 最近维护结果与后台状态 |
| `guard-installation.json` | 已安装维护服务的信息 |

正常撤销使用`rollback`，它只管理本工具安装的区块，并保留之后的无关配置修改。即使当前provider配置无效，回滚和事务恢复仍可直接读取受管状态与备份。已有用户自定义目录、旧版手动覆盖不会自动成为受管补丁。

安装或更新中断时运行：

```powershell
.\doctor.cmd recover
```

```sh
sh doctor.sh recover
```

`recover`仅在确认持锁进程已退出后清理操作锁，并检查配置路径、事务前备份和当前内容。当前配置须仍匹配事务前或事务后版本；中断后又被编辑时会停止，不能用旧备份强行覆盖。运行时安装锁和项目`.doctor-setup-lock`属于环境准备流程，不由`recover`处理。

需要手动恢复时：

1. 停止维护进程，避免Codex或其他工具同时保存配置；另外保存当前配置与状态目录。
2. 根据`active.json`中的`configPath`、`backupPath`、`block`，或`transaction.json`中的`restorePath`确认恢复对象。
3. 有后续配置修改时做差异合并。受管区块完整且唯一时，只移除下列两个标记之间的完整区块，并保留其他内容：

   ```text
   # >>> codex-tool-doctor managed protocol patch
   # <<< codex-tool-doctor managed protocol patch
   ```

4. 只有确认没有需要保留的后续编辑且备份校验一致时，才整体恢复相应备份。区块部分修改、重复、备份校验不符或目录属于其他管理者时，应先人工合并。
5. 状态完整时再运行`recover`或`rollback`完成工具状态清理；不要只删`active.json`或候选目录。重启Codex并新建会话检查配置。

备份包含原配置的完整内容，可能带有敏感字段，应按原配置的权限保管。公开问题报告只提供必要的脱敏诊断，不上传整份配置、认证文件、GUI令牌或备份。

## 6. 故障码与排查

报告的`result`、`blockers[].code`、终端验证的`failureKind`和进程退出码是不同层次。先确认失败发生在哪个阶段，再处理相应原因。

| 诊断结果或阻止码 | 含义与处理 |
| --- | --- |
| `network-error` | 连接、DNS、TLS、超时、中断或响应大小限制等请求失败；检查摘要及网络/CA配置 |
| `http-error` | 服务返回非200状态；结合HTTP状态判断，不能一律归为协议问题 |
| `parse-error` | JSON或Responses事件无法解析；检查是否返回HTML路由页或其他协议 |
| `stream-error` | 响应未正常结束、包含失败事件或出现孤立增量；检查服务流实现 |
| `no-tool`、`unexpected-output` | 未识别工具，或工具类型、名称、数量、标记不匹配；须结合平铺对照判断 |
| `insufficient-controls` | 平铺对照不足两轮；重新运行完整诊断 |
| `flat-control-failed` | 平铺工具也失败；先处理基础工具、连接或认证问题 |
| `no-format-evidence` | 没有包装格式特有证据；此补丁不能仅凭超时或服务错误安装 |

HTTP401/403先检查认证与访问权限，429检查额度或限流，普通5xx检查服务可用性。400/404/405/415/422/501只有在平铺对照连续正常、失败集中于包装格式时才可作为候选证据；尤其404还可能是端点错误。

| 终端验证`failureKind` | 含义与处理 |
| --- | --- |
| `permission-blocked` | 识别到执行策略、沙箱或访问权限阻止；检查目标运行环境，不算终端成功 |
| `timeout` | 本轮真实Codex未在时限内完成；检查请求、进程和工具结果回传 |
| `no-terminal-event` | 没有实际终端完成事件；模型文字不能代替工具执行 |
| `tool-result-not-acknowledged` | 命令完成后、回合完成前，没有同一条消息同时确认实际目录和本轮标记；检查工具结果回传 |
| `terminal-verification-failed` | 退出码、命令、目录、事件、额外工具或进程输出限制等其他判据未通过 |

`DOCTOR_ERROR`是没有专用错误码时的CLI包装，须阅读`error.message`；`ENOENT`表示文件或程序不存在，`EACCES`/`EPERM`表示访问受限，`ERR_PARSE_ARGS*`表示参数有误。管理区块冲突、报告过期、候选被修改等通常以中文错误消息说明。

`status.state`为`maintenance-required`时运行维护；`recovery-required`时先恢复事务；`conflict`时检查目录或区块的人工修改。`verified`表示已有匹配的安装验证记录，不表示已经实时检测服务端，也不涵盖所有工具。

| CLI退出码 | 含义 |
| --- | --- |
| `0` | 命令完成，仍需读取业务结果；例如`maintain`可能报告尚未安装补丁 |
| `1` | 参数、配置、准备环境、计划或应用等操作发生错误 |
| `2` | `diagnose`至少一个样本未通过，或`verify`未通过；诊断发现可修复差异时也可能返回2 |
| `78` | 共享启动器请求平台层补齐可用npm的内部信号，通常由平台入口处理，不是协议故障码 |

`launch`会转交目标Codex的退出码。GUI的401表示会话令牌无效，403表示Host/Origin检查失败，409表示已有操作运行；这些状态与上游API的同号状态应分开判断。
