# 设计说明

Codex Tool Doctor面向第三方API与Codex之间的工具协议兼容问题：客户端能够连接模型，不代表上游能够完整识别其工具定义。本工具通过可重复对照、候选模型目录和真实客户端验证，判断有限范围内的配置补丁是否适用。

安装与故障处理见[使用指南](使用指南.md)，测试和证据边界见[验证指南](验证指南.md)。

## 1. 目标与协议适用边界

工具调用链为：Codex构造Responses请求→第三方API或路由→模型返回工具调用→Codex执行本地工具→工具结果回传→模型完成本轮响应。

候选补丁针对其中一种兼容模式：普通function和平铺custom工具稳定通过，而namespace包装或输入中的additional_tools形式单独失败。它不能从外部断定服务商内部如何实现，只能根据相同端点、模型和凭据下的行为差异提供候选证据。

适用前提包括：

- 服务提供Responses兼容接口；仅有Chat Completions等其他接口不满足前提。
- 所选Codex能导出内置模型目录，并能实际加载`model_catalog_json`覆盖。
- 所选模型在目录中恰好有一个条目，且`use_responses_lite`原值为`true`。
- 候选目录被目标程序接受，随后两轮真实终端验证全部通过。

`use_responses_lite`属于目标构建的模型元数据，不能当作所有版本都保证存在的稳定公共接口。程序发现记录目标路径、版本、内容摘要和安装来源；安装依据实际能力与候选验证，不以固定构建摘要名单代替验证。

本工具不提供通用API协议转换，不修改Codex二进制，不接管API流量，不删除`call_id`或重写会话历史，也不保证全部namespace、MCP、插件、图像或文件编辑工具都恢复。超时、认证、限流、服务停机、证书与系统权限错误需要单独处理。

## 2. 主要技术决策

| 决策 | 技术理由与限制 |
| --- | --- |
| 复用Codex已有请求构造逻辑 | 通过模型目录选择协议分支，避免自行代理流量、重写事件和维护调用ID映射；效果依赖目标构建的实际实现 |
| 从目标程序导出完整目录，只改所选模型的一项字段 | 保留工具模式、上下文窗口等其余元数据；完整快照也意味着升级后必须重新生成 |
| 使用平铺工具作为对照 | 将包装格式兼容问题与整体服务故障区分；一次工具失败或一条`NO_TOOL`不能单独证明补丁适用 |
| 先隔离验证，再安装 | 无效候选不进入日常生效配置；目录能解析只验证加载能力，不证明终端可用 |
| 每个受管配置绑定一个目标程序 | 不让桌面端与CLI的不同构建共用不匹配目录；多安装场景使用独立配置目录或profile |
| GUI和CLI共享操作引擎 | 两种入口使用相同诊断、计划、验证和维护规则；GUI用本机浏览器，无需独立桌面运行时或前端框架 |
| 显式启用升级维护 | 配置补丁可持续保存，兼容性仍须重新验证；后台服务不是永久修复保证 |
| 平台引导脚本配合Node共享逻辑 | 缺少Node时仍能准备环境，核心业务跨平台复用；下载及系统运行条件仍受宿主限制 |

### 目录字段与请求位置

候选目录保留完整JSON，仅对选定模型做如下字段变化：

```json
{
  "use_responses_lite": false
}
```

该片段是模型条目中的变化，不是完整候选文件。`model_catalog_json`则是TOML配置顶层键，位于第一个表之前，由受管区块引用候选文件的绝对路径。不能把`use_responses_lite=false`直接写进provider表来代替目录补丁。

以下只是适用构建中的工具位置示意，省略了必需的工具描述、语法和会话内容，不可直接当作请求模板：

```json
{
  "input": [{
    "type": "additional_tools",
    "role": "developer",
    "tools": [{
      "type": "namespace",
      "name": "functions",
      "tools": [{ "type": "custom", "name": "exec" }]
    }]
  }]
}
```

在采用相应完整Responses分支的构建中，exec可能由客户端放入顶层工具列表：

```json
{
  "tools": [
    { "type": "custom", "name": "exec" },
    { "type": "function", "name": "wait" }
  ]
}
```

真实请求始终由Codex自己生成，其他普通函数命名空间可能仍保留。上述结构不是“删除所有命名空间”的规则，也不能证明任意客户端和上游组合都兼容。

## 3. 诊断与失败分类

诊断在同一模型、端点和凭据下发送4组请求，每组2～5轮，默认各2轮：

| 检测项 | 工具承载方式 |
| --- | --- |
| `function-flat` | 顶层function，返回JSON参数中的随机标记 |
| `custom-flat` | 顶层custom，用语法约束返回同一轮的随机标记 |
| `custom-namespace` | 顶层namespace包装custom |
| `custom-additional` | 输入中的additional_tools承载namespace/custom |

虚拟工具名为`diagnostic_echo`，工具输出只用于分类，不会交给终端执行。成功要求恰好一个工具调用，且类型、名称和标记匹配。

两组平铺对照都至少两轮且全部通过，包装格式至少出现一次明确失败，才得到`candidate-verification-required`。允许作为包装差异证据的结果包括`no-tool`、`unexpected-output`、`parse-error`、`stream-error`，以及HTTP400/404/405/415/422/501。

单独的连接错误、401/403、429或普通5xx不能作为这种证据。如果另一个包装请求已有明确差异，个别传输故障不会简单否决全部候选，但仍在`warnings`中记录；后续真实终端验证不能放宽。

报告保留逐轮样本、HTTP状态、请求ID、事件计数、分组统计、`blockers`和`warnings`。生成计划时从原始样本重新计算结论，不信任报告中可被单独修改的汇总布尔值。

响应解析覆盖普通JSON Responses对象和SSE，处理BOM、CRLF、`event:`字段及工具增量。缺少完成状态、包含失败事件、出现没有先建立条目的孤立增量，或一次返回多个诊断调用，都不会当作成功。诊断解析器的兼容范围不等于Codex自身解析器的兼容范围。

## 4. HTTP、TLS与凭据

地址解析和网络传输使用同一协议判断，根据URL选择Node的`http`或`https`模块。只解除HTTPS限制但仍使用`https.request`不能支持HTTP。路径拼接先在局部字符串中去除尾斜杠，再一次性设置`URL.pathname`，避免空路径自动规范化为`/`后产生`//responses`。

工具不扫描猜测端点，不擅自补`/v1`，不跟随诊断请求的重定向。公网HTTP需要显式允许；默认本地判断基于主机名或IP字面值，不是对DNS解析结果的网络安全认证。

HTTPS保留证书验证，自建CA可配置Node的额外信任库。该设置只说明Node进程的信任行为，不替代真实Codex后端或平台下载器自己的CA配置。诊断传输默认超时30秒，最大响应为2,000,000字节，并按UTF-8字节数设置请求Content-Length。

凭据按显式环境变量、显式Bearer、API密钥来源的规则读取，明确无认证的路由不借用账户令牌。不执行外部凭据助手，不使用ChatGPT会话令牌。自定义头拒绝换行与关键传输头覆盖。

诊断输出会遮蔽已知凭据、请求头值、查询参数值和常见令牌形式；脱敏不是任意字符串均可安全公开的保证。原始配置备份可能包含敏感内容，计划和验证报告也可能包含环境信息，公开前仍须筛选必要字段。

## 5. 候选、验证与安装事务

1. 读取配置、模型、端点与选定程序；检查诊断报告与当前上下文一致。报告有效期为24小时，时间异常也会拒绝。
2. 导出当前构建的内置目录，仅修改所选模型字段；保存候选、原配置和计划。目标程序必须实际解析候选，并读回`use_responses_lite=false`。
3. 在所选状态目录创建临时配置和专用工作目录。隔离配置围绕所选模型、provider、所需API认证和候选目录构建，不照搬个人MCP、插件、旧会话或项目脚本。
4. 每轮启动独立的短时Codex会话，使用read-only沙箱、临时会话和禁止审批提示的配置，关闭插件功能，只请求一次只读目录命令。验证继承进程环境，因此不是用于运行任意不可信程序的安全容器。
5. 两轮都必须看到恰好一个有效`command_execution`完成事件、命令退出码0和输出中逐行匹配的实际工作目录。模型必须在命令完成后、`turn.completed`之前，在同一条回复中确认实际目录与本轮随机标记。提前回复、只回显标记、复用前轮标记或出现错误事件、文件变更、MCP及网页搜索事件等均不通过；模型文字不能替代终端事件。
6. 安装前重新核对程序路径和内容、配置上下文、端点、模型、候选内容及生效补丁状态。验证记录须与当前计划匹配、两轮全过，且不超过30分钟。
7. 取得操作锁，保存恢复基线、事务前完整配置和`transaction.json`，再原子替换生效配置、写入`active.json`，最后删除事务日志。更新补丁沿用同一安装事务流程。

窗口期内失败时按事务日志恢复；进程中断后由`recover`检查。恢复仅接受当前配置仍为事务前或事务后内容的情况，中断后有人编辑配置时保留现场。

SHA-256用于绑定文件内容和发现过期、冲突、误改，不是数字签名或防恶意篡改系统。状态目录、目标程序及配置须由受信任的本地用户管理；替换多个文件也不是跨文件数据库事务或断电持久性保证。

`operation.lock`记录持锁PID，`recover`只在确认进程不存在时移除锁，权限不足或锁无效时不冒认进程已退出。GUI在单实例内串行操作，配置修改还有文件锁与写入前检查；其他程序并不遵守这个锁，因此仍应避免同时保存配置。

### 回滚与手动目录

回滚在操作锁内校验备份并检查当前区块。当前配置没有后续变化时可恢复基线；存在无关编辑时，只移除唯一且完整的受管区块，再解析TOML并原子写回。区块部分修改、重复或备份内容不匹配时停止。

安装和更新有专门的事务日志；回滚使用锁、配置一致性检查、原子写入和回滚记录，不能据此推断所有状态文件在任何中断情况下都会整体提交。

手动添加的`model_catalog_json`不自动产生`active.json`，因此不能依赖`rollback`撤销任意手动覆盖。开发辅助脚本`scripts/prepare-catalog.mjs`只生成新候选并检查加载，不覆盖同名文件，也不安装配置。常规用户应使用`plan`和`apply`，手动候选可通过平台入口的`verify --catalog`评估，但不能代替正式安装所需的计划匹配检查。

## 6. 维护生命周期

外置目录是一份完整模型元数据快照。维护比较所选程序内容与路径、内置目录、模型及相关配置，并检查受管区块和候选内容。无变化时沿用已有验证记录，不请求API；服务端独立变化由显式`--recheck`触发复检。

维护可以重新验证后恢复完整移除的受管覆盖，或重建丢失的目录；部分人工修改及外部覆盖会阻止自动操作。新候选失败保留旧补丁和配置，旧补丁是否仍可用须单独判断。

原生目录已将字段设为`false`，或服务4组诊断均通过时，维护将未修改的内置目录作为候选，仍通过两轮终端验证后才回滚覆盖。只有该验证成功并完成移除，才产生`native-supported`结果；不能根据字段值或模拟测试宣布原生成功。

`guard`以用户选择的间隔运行维护，无变化不请求API，失败采用最长1小时的退避。系统服务显式安装，绑定配置/profile及运行时、项目路径；服务不保存API密钥值，认证和CA环境必须对服务进程可见。后台不会中止旧会话或主动弹窗。`launch`提供维护后再启动目标程序的入口。

## 7. GUI安全边界

本机浏览器GUI与CLI调用同一个`engine`。服务仅监听回环地址，静态资源和API都检查Host及存在时的Origin；API额外验证随机会话令牌，通过URL fragment交给前端，不把令牌放在查询参数中。

界面设置CSP、禁止嵌入框架和缓存，限制操作种类、路径长度、请求体大小与并行作业。它没有远程管理或公开部署设计；本机恶意进程、浏览器扩展和拥有同用户文件权限的其他软件不在该令牌机制的隔离范围内。

## 8. 平台移植与环境准备

| 层次 | Windows | macOS/Linux |
| --- | --- | --- |
| 无Node时的引导 | CMD入口调用Windows Script Host的JScript | POSIX sh |
| 共享依赖准备与业务 | `scripts/launch.mjs`及Node核心 | 同一套Node模块 |
| 原生程序发现 | 桌面端缓存、npm原生包、PATH或显式路径 | PATH、符号链接、npm原生包；macOS增加应用包资源目录 |
| 终端验证 | PowerShell7的`Get-Location` | `pwd` |
| 用户维护服务 | 任务计划 | macOS的LaunchAgent、Linux的systemd用户服务 |

Windows启动器本身不要求PowerShell7，它通过系统脚本宿主选出Node，再由`doctor.cmd`直接启动Node以保留控制台输入输出。运行时路径通过UTF-8临时响应文件传递，避免标准输出经系统代码页解码损坏中文路径。文档中的Windows交互命令使用PowerShell7，不额外嵌套PowerShell宿主。

Windows解压使用脚本宿主设置Unicode工作目录，再向tar传递ASCII归档相对名称，避免依赖tar对中文命令行路径及系统代码页的处理。成功或失败均恢复原工作目录，只有完整运行时通过校验后才发布到稳定缓存。

POSIX入口保持参数边界和交互stdin。Linux应使用当前系统的原生程序，不混用另一平台的Node或Codex二进制。程序发现会解析符号链接和npm JavaScript启动器背后的原生后端；显式目标必须可执行，并能返回Codex版本和模型目录。

POSIX脚本在变量名紧邻中文的位置使用`${name}`明确边界，避免macOS系统shell在某些locale下把后续多字节字符计入变量名。语法检查不足以发现这类问题，平台验证还需实际执行缺少Node时的安装分支。

共享启动器判断是否直接执行时，将入口路径和ES模块地址两侧都解析为真实文件路径后再比较。这使Windows长短路径、目录链接和macOS的`/var`路径别名也能进入启动流程，避免进程退出码为0却没有启动应用。

移植环境准备时保持以下顺序：检查系统Node→检查所有适用缓存→选择平台/架构清单项→取得安装锁→HTTPS下载并核对摘要→暂存解压并检查Node/npm→发布稳定目录→进入共享启动模块。

运行时清单每项包含版本、归档名和SHA-256，随软件维护，不在启动时执行远程安装脚本。下载器只允许HTTPS及HTTPS重定向；这是运行时下载策略，与诊断请求完全不跟随重定向的策略不同。未通过校验和运行检查的目录不会交付给其他启动器，安装竞争受独立运行时锁保护。

共享启动模块只依赖Node内置模块，检查依赖声明版本与实际导入。修复依赖时通过当前Node运行`npm-cli.js`，使用锁文件及`--ignore-scripts`，避免生命周期脚本和不同平台npm包装器的转义差异。npm缺失或不能执行时返回内部退出码78，要求平台层准备完整运行时；其他应用退出码按原意返回。

稳定运行时目录供后续启动和维护服务复用，不在每次启动时更新或删除。运行时安全升级需要维护清单，并执行干净环境检查；新增平台须同时核对下载、摘要、解压、可执行性、路径编码、参数、stdin、并发锁、服务定义和真实后端行为。

macOS/Linux相关代码和测试夹具不能代替相应系统实机验收，详见验证指南。不能通过绕过能力检查、复制其他平台目录或降低验证权限来宣布支持。
