# 验证指南

本指南说明如何复现协议故障、运行自动化测试，以及严格验收真实Codex终端调用。测试通过只证明对应测试范围；模拟事件、真实网络连接、真实Codex进程和真实模型服务是不同层次，不能互相替代。

日常操作见[使用指南](使用指南.md)，判断规则见[设计说明](设计说明.md)，开发准备见[参与开发](../CONTRIBUTING.md)。测试和mock脚本需要源码目录及开发者可用的Node.js22或更新版本；用户发布包不包含测试和mock服务。下文开发命令可使用`node`/`npm`，用户操作使用`doctor.cmd`或`sh doctor.sh`。

## 1. 验证层次与成功含义

| 层次 | 实际运行内容 | 可以证明 | 不能证明 |
| --- | --- | --- | --- |
| 单元与故障夹具 | 确定性样本、模拟后端事件或替代系统命令 | 分类、验证判据、完整性检查和异常分支 | 真实模型或终端已经执行成功 |
| 本地HTTP/HTTPS | Node服务真实监听回环端口，返回模拟Responses数据 | 请求路径、编码、TLS信任与失败行为 | 第三方服务或Codex自身TLS配置兼容 |
| 生命周期测试 | 真实验证器与文件操作，配合可控模拟Codex事件 | 候选、安装、维护、回滚和恢复逻辑 | 原生Codex成功执行工具 |
| 真实Codex连接mock | 原生Codex进程访问本地模拟服务 | 目录加载、协议往返；严格模式通过时还包括真实终端和回滚 | 真实模型能够正确生成同样调用 |
| 真实Codex连接目标API | 所选客户端、模型、服务和当前配置 | 该组合在验收时的终端调用及结果回传 | 所有版本、所有工具或未来协议变化都兼容 |
| 平台环境与用户服务 | 各平台实际启动器、下载、GUI及系统服务 | 对应平台实际执行过的安装与运行行为 | 其他平台或仅生成过服务文件的场景也通过 |

已有验证资料覆盖真实Codex加载候选并与本地mock完成Responses往返，也覆盖权限阻止的识别及保持原配置。它们不提供真实终端两轮成功的结论。终端成功、第三方真实API成功和原生无需补丁成功，均需按下面的严格标准另行取得证据。

## 2. 运行自动化测试

在源码根目录的开发终端执行：

```sh
npm ci --ignore-scripts
npm test
```

`npm test`运行Node内置测试执行器，等价于`node --test`。先确认当前终端没有遗留`TOOL_DOCTOR_INTEGRATION_BINARY`或`TOOL_DOCTOR_TEST_NETWORK=1`，否则会启用相应可选检查。普通测试不请求付费模型，不修改个人Codex配置，也不安装用户维护服务；会创建隔离目录并监听回环端口。

需要单独复验某类行为时可运行已有测试文件，例如：

```sh
node --test test/config.test.mjs test/probe.test.mjs test/transport.test.mjs test/https.test.mjs
node --test test/patch.test.mjs test/lifecycle.test.mjs test/gui.test.mjs test/guard.test.mjs
node --test test/bootstrap.test.mjs test/bootstrap-posix.test.mjs test/bootstrap-windows.test.mjs
node --test test/release.test.mjs
```

| 范围 | 关键检查 |
| --- | --- |
| 配置与传输 | HTTP/HTTPS、回环/IPv6/局域网、路径前缀、认证头、查询参数、超时、重定向及大小限制 |
| 协议分类 | 命名空间格式拒绝、畸形JSON/SSE、未识别工具、认证限流、服务故障和平铺对照失败 |
| 候选完整性 | 过期报告、修改汇总、候选内容变化、配置/目标变化及两轮验证记录匹配 |
| 生命周期 | 验证失败不安装、升级失败保留旧补丁、目录丢失、区块移除、并发、回滚保留其他编辑及中断恢复 |
| GUI | Host/Origin/令牌校验、接口参数、未知操作与并行操作拒绝 |
| 启动与服务 | 参数及路径转义、环境准备、缓存复用、下载拒绝、服务文件生成；模拟和原生检查分别统计 |
| 发布包 | 归档格式、路径和包含范围，用户包与开发测试文件的分离 |

测试出现`skip`必须记录具体原因。没有设置真实后端、不是原生目标平台、缺少POSIX shell或没有显式允许联网，都可能使相应项目跳过；跳过不算该范围通过。

## 3. 用mock复现故障

mock只监听`127.0.0.1`，不请求真实模型，不需要API密钥。开发终端A运行：

```sh
npm run mock-router -- 8787 namespace-rejected
```

| 模式 | 诊断阶段的行为 | 预期判断 |
| --- | --- | --- |
| `namespace-rejected` | 平铺通过，包装形式返回422 | 允许候选验证 |
| `malformed-stream` | 平铺通过，包装形式返回畸形SSE | 允许候选验证，并保留解析警告 |
| `no-tool` | 平铺通过，包装形式返回`NO_TOOL` | 允许候选验证 |
| `outage` | 所有诊断格式返回503 | 平铺对照失败，阻止候选 |
| `healthy` | 4组虚拟工具均通过 | 没有包装特有故障证据，不推荐补丁 |

这些模式控制虚拟诊断响应，不是对真实模型行为的仿真保证。`healthy`也不自动证明原生Codex可用。

终端B创建独立测试配置。Windows示例使用PowerShell7：

```powershell
$testHome = Join-Path ([IO.Path]::GetTempPath()) ('doctor-mock-' + [guid]::NewGuid())
New-Item -ItemType Directory -Path $testHome | Out-Null
@'
model = "fixture-model"
model_provider = "mock"
[model_providers.mock]
name = "本地模拟Responses"
base_url = "http://127.0.0.1:8787/v1"
wire_api = "responses"
requires_openai_auth = false
'@ | Set-Content -LiteralPath (Join-Path $testHome 'config.toml') -Encoding utf8
.\doctor.cmd diagnose --home $testHome --json
```

macOS/Linux示例：

```sh
test_home=$(mktemp -d)
cat > "$test_home/config.toml" <<'TOML'
model = "fixture-model"
model_provider = "mock"
[model_providers.mock]
name = "本地模拟Responses"
base_url = "http://127.0.0.1:8787/v1"
wire_api = "responses"
requires_openai_auth = false
TOML
sh doctor.sh diagnose --home "$test_home" --json
```

查看测试配置下`tool-doctor/last-report.json`的`samples`、`summary.byKind`、`blockers`与`warnings`。前三种模式的`diagnose`退出码2表示确实发现失败样本，仍可能得到候选建议，不能只用退出码判断检测器是否出错。

上述`fixture-model`仅用于诊断，不要求安装Codex。继续测试计划和安装时，必须选择原生程序实际存在且满足补丁前提的模型；优先使用下一节集成测试自动管理隔离配置。连接mock后执行验证仍可能真的运行只读终端命令，不能将“没有调用付费模型”误解为“没有本地执行”。

停止模拟服务用Ctrl+C。所有操作始终指定测试配置，不能将日常Codex地址改为mock地址。测试结束可清理自行创建的临时目录，不删除个人配置。

## 4. 真实Codex连接mock的严格验收

这项集成检查需要所选平台的原生Codex可执行文件。测试夹具使用模型`gpt-6-astra`，要求目标内置目录包含该模型且`use_responses_lite=true`；缺少对应能力时应如实记录不适用，不能跳过能力检查或复制其他构建目录来绕过。

在专门的开发终端中，将占位符替换为目标程序的绝对路径，然后同时设置两个变量。Windows：

```powershell
$env:TOOL_DOCTOR_INTEGRATION_BINARY = '<Codex原生可执行文件的绝对路径>'
$env:TOOL_DOCTOR_REQUIRE_TERMINAL = '1'
node --test test/integration.test.mjs
```

macOS/Linux：

```sh
TOOL_DOCTOR_INTEGRATION_BINARY='<Codex原生可执行文件的绝对路径>' \
TOOL_DOCTOR_REQUIRE_TERMINAL=1 \
node --test test/integration.test.mjs
```

Windows验证需要PowerShell7；macOS/Linux使用`pwd`。上述Windows变量只影响当前终端及其子进程，用完关闭该专用终端即可，避免影响后续普通测试。

`TOOL_DOCTOR_REQUIRE_TERMINAL=1`必须与有效的`TOOL_DOCTOR_INTEGRATION_BINARY`一起使用。只设置严格标志却未指定程序，集成项仍会跳过；这不满足严格验收。

测试使用隔离配置和回环mock，流程包括导出内置目录、解析候选、真实验证、执行修复、追加无关配置注释以及回滚保留该注释。所有请求应到达约定的`/router/v1/responses`，不访问真实付费模型。

未设置严格标志时，测试允许一种明确的非成功分支：后端已接受候选并发出工具请求，但系统策略阻止终端执行。测试检查`permission-blocked`和原配置未改变后可以通过；这表示错误识别正确，绝不表示终端成功。严格模式下同一情况必须失败，不能降低沙箱或提升权限来制造通过结果。

成功记录至少须确认：测试未跳过、严格标志生效、真实终端两轮通过、修复完成、回滚保留额外编辑。该结果仍只覆盖真实Codex与mock组合。

## 5. 真实第三方API验收

真实API验收会消耗服务额度。使用独立配置目录，按使用指南填写真实模型、端点、认证与CA配置，只复制必要字段。选择实际出问题的Codex后端，并保持整个流程的`--home`、`--profile`和`--binary`一致。

先用未加目录补丁的配置检查原生行为。以下是Windows命令示例；macOS/Linux将入口替换为`sh doctor.sh`：

```powershell
.\doctor.cmd inspect --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd verify --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd diagnose --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
```

原生两轮已经通过时记录该组合无需补丁，不为取得安装结果强行修改。原生失败时先区分协议、网络、认证和权限原因；只有对照满足候选条件才继续：

```powershell
.\doctor.cmd plan --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd apply --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd verify --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd status --home "<验收配置目录>" --json
```

各命令逐条确认结果。`apply`自行执行匹配候选的两轮验证，不复用另一程序、另一个端点或过期记录。成功应同时具备：

- `last-verification.json`的`passed=true`，两轮结果均通过，且目标、模型、端点、配置和候选绑定一致。
- 每轮有真实终端完成事件、退出码0和正确工作目录；命令完成后、回合结束前，同一条模型回复确认实际目录与本轮随机标记；没有额外工具或失败事件。
- `active.json`及受管区块存在，`status`显示目录、区块、模型和端点匹配。
- 应用后验证当前配置仍通过；对应Codex重启并新建会话后，实际所需场景另行确认。

候选目录加载、HTTP200、模型声称执行成功、GUI显示操作完成，任何单项都不能替代以上判据。终端验收也不能扩展为编辑、图像、MCP或全部插件已验证。

维护和回滚在同一验收配置中检查：

```powershell
.\doctor.cmd maintain --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd maintain --recheck --home "<验收配置目录>" --binary "<Codex原生可执行文件>" --json
.\doctor.cmd rollback --home "<验收配置目录>" --json
```

无变化的维护应报告不请求API；主动复检须重新验证。回滚后应恢复去除受管覆盖的配置，并保留测试期间添加的无关注释或设置。未发生中断时不要人为修改个人事务文件来测试`recover`，恢复分支优先使用自动化故障夹具。

声明`native-supported`需要真实验证未修改的内置目录并完成覆盖移除。模拟服务的`healthy`、目录字段为`false`或模拟生命周期测试通过，都不能单独形成这种结论。

## 6. 环境准备、HTTPS与平台检查

开发环境中运行干净安装检查：

```sh
npm run test:bootstrap
```

该检查需要联网，在隔离目录忽略系统Node，真实下载固定清单中的便携Node/npm、补齐依赖、再次启动检查缓存复用、破坏测试副本依赖后检查修复，并启动GUI确认回环HTTP可访问。不会卸载系统Node或改变全局PATH，结束后清理自己创建的临时目录。

POSIX平台的单独官方下载检查还可显式启用：

```sh
TOOL_DOCTOR_TEST_NETWORK=1 node --test test/bootstrap-posix.test.mjs
```

这项需要原生macOS/Linux宿主；在其他系统用POSIX shell模拟平台选择，不等于对应系统完成实机安装。Windows WSH夹具中的模拟系统组件也须与真实Windows下载检查分开记录。

HTTPS测试使用专用回环测试CA和服务证书，在独立Node子进程中分别验证额外信任成功、默认信任库拒绝证书。测试证书及私钥只用于本地测试，不用于生产服务，也不据此判断Codex后端的证书信任。

GUI接口测试不等于浏览器视觉检查。需要交互复验时，开发者可运行`node scripts/gui-fixture.mjs`，使用其输出的完整地址检查诊断、候选展示、错误反馈、JSON导出和窄屏布局；该夹具连接mock，不能据此声称真实服务修复成功。

用户维护服务须在对应平台的专用测试配置中分别检查安装、立即启动、登录触发、认证/CA环境、失败状态和卸载。生成任务XML、plist或systemd单元并通过解析或字符串断言，只证明定义层检查，不证明服务已经运行。

CI定义Windows、macOS、Linux与Node22/24矩阵，运行测试、依赖审计、命令帮助和打包检查，Node24任务另外执行干净安装检查。判断平台完成情况应依据对应版本的实际运行结果；CI定义存在不表示真实Codex或真实第三方API验收通过。

## 7. 对外记录验证结论

公开验证说明只保留可复现条件与结论：工具版本、系统及架构、Node/Codex版本、模型、HTTP或HTTPS、模拟/真实服务类别、测试命令、严格模式是否启用、通过/失败/跳过范围，以及功能限制。

不要发布本机用户名、绝对目录、机器构建摘要、密钥、认证头、完整配置、备份、GUI令牌或带凭据的URL。报告内用于本地完整性检查的摘要可以保留在本机，公开结论无需粘贴。仅记录模型目录加载或权限识别时，按实际范围表述，不写“原生终端修复成功”。

测试数量、依赖审计和CI状态以实际验收输出为准，不把过往数字或某个平台的结果当作所有环境的固定保证。
